# 2026-10-15：答案校验与跨来源组合证据修复

## 修复目标

本轮针对之前代码审查中两项核心问题：

1. **answer 与 claims 脱节**：生成模型可能给出一组真实但与最终短答案不一致的声明，旧验证器只检查声明，会误放行最终答案。
2. **跨来源多实体拒答**：旧验证器要求带有多个实体 ID 的声明在每一个单一证据窗口里同时出现所有 ID，导致真正多跳所需的分散证据被机械地清空。

## 已实施

- 新增 answer_guard.py：对短答案中的一项或数项（如“2023，南京”）要求在**同一条已审查声明**中出现正向锚点；排除部分明确否定提及、英文单词子串误匹配。仅对 verify/full 分支生效，baseline/adaptive 答案保持原状。拒绝时 verification.reason 为 answer-claim-mismatch，保留候选答案供审计。
- verifier.py 对同时包含多个不同字母数字项目 ID 的声明，从各相关来源挑选少量句子，构造**上限 12 个**组合证据窗口，交给现有 NLI 模型做真正的关系蕴含判断。缺失任一 ID 仍不能通过；组合并不自动表明事实成立。
- verdict 在旧 support_id / contradiction_id 之外增加 support_ids / contradiction_ids；pipeline 负责将组合证据的全部来源 ID 列入最终 citation_ids。
- 新增 test_answer_guard.py 和 test_multisource_verifier.py 回归测试。现有跨实体假矛盾测试必须继续通过。

## 验收和局限

在 Python 本地 pytest 中，历史测试与新增测试合计 37 项通过（依赖环境的导入路径采用 PYTHONPATH=src）；GitHub Actions 的独立结果以实际任务执行为准。

**不能将本轮测试当作新的 DeepSeek+GPU NLI 准确率。** 以下风险仍存在：

- 正向答案锚点是**字面一致性限制**，不是语义同义词推理。比如“美国/USA”、昵称、同义改写可能被误拒答；反向否定或跨句隐含否定也未被完整识别。需要在独立 validation 集上研究更稳妥的语义替代方案。
- 多源证据被并列输入 NLI，不表示模型有可靠的跨文件逻辑推断能力；此改动只是移除了“所有 ID 必须同段出现”的结构性阻断。上限 12 组候选仍可能遗漏关键路径。
- 若模型自行选择与问题无关的已支持 claim，答案虽然与之字面一致仍有可能错误；“与问题相关”需要单独的问句/断言语义对齐评估。
- 当前公开 GitHub 工程仍以 Ollama 适配为主，用户以前运行的 DeepSeek/CUDA 部署源码位于封存实验包的 deployed_source.tar.gz，尚不能将两者视为完全等价的部署。

后续工作顺序：先核对部署代码差异和集成环境 → 在真实验证集上评估拒答覆盖率及错误接受率 → 冻结参数后执行新盲测。
